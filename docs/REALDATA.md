# 실차 데이터로 시뮬레이터 점검

실제 주행의 운동(IMU, CAN 속도)에 합성 승객과 실내 설정을 붙여, 시뮬레이터 데이터와 같은 방법으로 피처와 라벨을 만들고 비교했습니다. 멀미 라벨은 실차 데이터에도 없으므로 라벨은 시뮬레이터와 같은 Oman 공식으로 만듭니다. 그래서 이 비교로 알 수 있는 것은 **운동 분포가 얼마나 다른지**와 **시뮬레이터로 학습한 모델이 실제 운동에서도 순위를 잘 매기는지**입니다. 실제 멀미를 맞히는지는 알 수 없습니다.

데이터셋 조사는 [DATASETS.md](DATASETS.md)에 있습니다.

## 1. 데이터 상태

| 데이터 | 상태 | 비고 |
|---|---|---|
| comma2k19 Chunk_1 | 받음, 변환, 비교 완료 | MIT. 영상 없이 신호만 140 MB. 5분 이상 이어진 구간 19개, 2.9시간 |
| BATON-Sample | 받음, 변환, 비교 완료 (4장) | CC BY-NC 4.0. CSV 두 종류 2.1 GB. 5분 이상 경로 34개, 19.1시간, **운전자 폴더 2개** |
| BATON 전체 | 아직 없음 | 수동 승인. 41 GB라 경로별로 받아 처리해야 함 |

**BATON 저장소(github.com/OpenLKA/BATON)에는 데이터가 없습니다.** 코드(베이스라인)와 문서만 있고, 데이터는 Hugging Face에 있습니다.

- `HenryYHW/BATON-Sample`: 페이지에는 43개 경로, 운전자 43명, 약 20개 차종, 약 15시간이라고 되어 있습니다. 받아 보니 폴더는 `driver_54`, `driver_97` 두 개뿐이고, 경로는 41개(차량 신호가 있는 것 35개), 약 19시간입니다. gated(약관 동의하면 자동 승인)
- `HenryYHW/BATON`: 페이지에는 565개 경로, 운전자 150명, 99개 차종, 162.1시간이라고 되어 있습니다(예전 README는 781개, 204.9시간). 수동 승인
- 라이선스는 CC BY-NC 4.0(비상업)입니다.

약관 동의와 로그인은 본인 계정으로 해야 합니다. 동의한 뒤에는 아래 순서로 받습니다(CSV만, 영상 제외).

BATON-Sample로 확인한 것 (리더 `ml/realdata/baton.py`에 반영)

- IMU는 기기 축 그대로라 정차 때 accel_x가 +9.8입니다(센서 x가 위쪽). 축 정렬이 기울기 약 87°를 찾아 돌립니다.
- vEgo에는 정차 중 0.4초쯤 79.9 m/s로 튀는 값(CAN 무효값)이 있습니다. 3초 중앙값에서 5 m/s 넘게 벗어난 샘플은 지우고 보간합니다.
- gas/brake 단위가 차마다 다릅니다(0~0.6, 0~200 등). 그래서 0~1 페달 칸에 넣지 않습니다. 크루즈(cruiseState_enabled)는 넣습니다.
- 운전 보조 작동(cc_latActive 또는 cc_longActive)은 태그로 남겨 사람 운전과 나눠 봅니다.

HF 저장소 목록(공개 API)으로 확인한 크기입니다. 영상이 대부분이라 위 명령처럼 두 파일만 받습니다. 저장소 폴더는 `driver_N/route_M/`입니다(README의 3단 구조와 다름).

## 2. 변환 방법 (`ml/realdata/`)

| 파일 | 하는 일 |
|---|---|
| `fetch_comma2k19.py` | comma2k19 청크 zip(약 9 GB)에서 HTTP range 요청으로 IMU·CAN·pose 파일만 받기. CRC 확인 |
| `comma2k19.py`, `baton.py` | 데이터셋별 리더. 연속 구간마다 `{acc, gyr, speed, extra}` 하나 |
| `convert.py` | 축 정렬, 100 Hz 리샘플, trip.bin 행, 라벨용 운동학 |
| `build_real.py` | 구간마다 합성 승객 4명 → `featurize` → `build_dataset.ride_record` (시뮬레이터와 같은 함수) |
| `compare.py` | 실차 대 시뮬레이터 비교표, 시뮬레이터 모델을 실차 행에 적용 |

**축 정렬 (`convert.align`).** 기기를 차에 단 방향을 데이터에서 추정합니다. P1 장착 보정(T-04, T-11)에도 그대로 쓸 수 있습니다.

1. 정차 구간의 평균 가속도를 중력으로 보고 +z로 돌립니다.
2. 수평 회전은 IMU 수평 가속도를 CAN 기준 [dv/dt, v·ω_z]에 최소제곱으로 맞춰 정합니다.
3. 정차 구간 자이로 중앙값을 바이어스로 뺍니다.
4. 정차한 곳의 경사가 남기는 기울기는 주행 중 평균 (IMU 수평 − 운동학)이 0이 되도록 한 번 더 돌려 없앱니다.

`ml/tests/test_realdata.py`에서 시뮬레이터 주행을 앞·오른쪽·아래 축으로 바꾸고 피치 4°, 요 7°를 더해 돌려 놓은 뒤 원래대로 되돌아오는지 확인합니다. comma2k19에서 나온 값은 다음과 같습니다.

| 항목 | 최소 / 중앙 / 최대 |
|---|---|
| 기기 기울기 (센서 z와 중력 사이) | 2.9° / 4.0° / 7.1° |
| 4단계 추가 보정 | 0.1° / 1.2° / 2.6° |
| 센서 x와 차량 앞 사이 각 | −2.8° / 1.3° / 3.2° |
| 상관 (IMU 대 CAN), 종방향 | 0.58 / 0.85 / 0.96 |
| 상관 (IMU 대 CAN), 횡방향 | 0.81 / 0.93 / 0.98 |

4단계가 없으면 급제동 횟수가 IMU 기준으로 부풀었습니다 (한 구간에서 CAN 기준 4회, IMU 기준 13회).

**라벨.** 시뮬레이터 `label()`과 같습니다. 입력만 실제 값으로 바꿨습니다. a_long은 CAN 속도의 미분, a_lat은 v·ω_z입니다. 승객은 시뮬레이터와 같은 승객 풀(seed 0, 120명)에서 구간마다 4명을 뽑습니다. 공조와 좌석은 `sim.gen_ride`와 `sim.cabin_rows`로 붙입니다.

### comma2k19 해석

1. **시뮬레이터 운전이 실제보다 거칩니다.** 같은 시내 속도대에서도 종방향 가속 RMS가 1.4배, 저크가 1.6배, 급제동이 약 2배입니다. `sim_config.json`의 운전자 가감속 범위, 정차 빈도, 속도 흔들림이 큰 쪽에 치우쳐 있습니다.
2. **고속도로가 없습니다.** 시뮬레이터 구간의 목표 속도가 최대 80 km/h(운전자 계수를 곱해도 92 km/h)이고, 짧은 구간 사이 가감속 때문에 1분 평균이 80 km/h를 넘는 일이 없습니다. 실제 고속 주행은 종방향은 조용하지만 횡방향 흔들림(차로 유지, 완만한 곡선)이 시내보다 큽니다 (rms_y 0.13 대 0.08).
3. **시뮬레이터에는 약한 상시 흔들림이 없습니다.** 직선 구간의 횡방향이 정확히 0이고(rms_y p10 0.00), 수직 저주파 성분(노면 굴곡, 차체 상하 운동)도 없습니다(rms_z 0.003 대 0.02~0.06). 시뮬레이터의 노면 진동은 2~15 Hz라 Wf(멀미 가중, 0.5 Hz 이하가 주로 통과)를 거의 통과하지 못합니다.
4. **급회전은 시뮬레이터가 더 많습니다.** 회전교차로와 S자 곡선 때문에 rms_y와 yaw의 꼬리가 실제보다 깁니다 (p90 0.49 대 0.23).
5. **그래서 실차 라벨 비율이 낮습니다.** 같은 시간 범위에서 P(≥4)가 0.048로 시뮬레이터(0.117)의 절반이 안 됩니다. 고속도로 비중이 큰 영향이 큽니다.
6. **모델은 실제 운동에서도 순위를 잘 매깁니다.** ROC-AUC가 0.84~0.92로 시뮬레이터 교차검증과 비슷하거나 높습니다. 평균 예측 확률도 실제 비율에 가깝습니다 (0.216 대 0.207, 0.063 대 0.048). PR-AUC가 낮은 것은 양성 비율이 낮아서입니다. 운동 분포가 이만큼 달라도 모델이 무너지지 않는다는 뜻입니다. 다만 라벨이 같은 Oman 공식에서 나왔으므로, 실제 멀미에 대한 검증은 아닙니다.

**한계.** 차 한 대, 운전자 한 명, 주로 캘리포니아 고속도로입니다. 구간은 최대 15분이라(Chunk_1) Oman의 느린 시간상수(502초)에 비해 짧고, 탑승 초반만 봅니다. 행은 1,788개(구간 19개, 탑승 60회)로 적습니다. 같은 구간의 승객 4명은 운동이 같아 행끼리 독립이 아닙니다. 피처 77개 중 54개만 채워집니다. 페달, EV, 내비 신호가 없고, 공조와 좌석은 합성입니다.

**해석**

1. **앞뒤 방향이 거칠다는 결론이 세 출처에서 같습니다.** 시뮬레이터의 rms_x와 저크 중앙값은 BATON 두 운전자와 comma2k19 시내 구간보다 약 2배 크고, 급제동은 2배 안팎입니다. 운전자가 달라도 실제 값끼리는 서로 비슷합니다(0.16~0.25). 시뮬레이터 보정(T-23)의 첫째 목표로 삼아도 됩니다.
2. **좌우 방향은 중앙값이 맞고 꼬리만 깁니다.** rms_y 중앙값은 0.11 대 0.09로 비슷합니다. 시뮬레이터는 직선에서 정확히 0이고(p10 0.00 대 0.01), 급회전 꼬리가 깁니다. comma2k19와 같은 결과입니다.
3. **누적량은 생각보다 가깝습니다.** 경로가 길면 MSDV와 Oman 점수 분포가 KS 0.2 수준으로 가까워집니다. 그래도 라벨 비율은 시뮬레이터가 높습니다(P(≥4) 0.37 대 0.20).
4. **고속도로와 긴 정차가 없습니다.** 시뮬레이터에는 80 km/h 이상이 0%이고, 5분 중 정차 비율 꼬리가 짧습니다(p90 0.30 대 0.63).
5. **모델은 순위는 잘 매기지만 확률을 과대평가합니다.** ROC-AUC는 0.83~0.86으로 시뮬레이터 교차검증과 비슷합니다. 평균 예측 P는 실제 비율보다 높습니다(k4 0.33 대 0.20). 시뮬레이터 운동이 거칠어 학습한 확률 수준 자체가 높기 때문으로 보이고, 보정하면 줄어들 것으로 예상합니다. comma2k19에서는 이 차이가 작았습니다(0.063 대 0.048).
6. **운전 보조 주행은 표본이 작습니다.** 972행, 탑승 16회이고 80%가 고속도로입니다. 앞뒤 흔들림이 사람 운전의 약 1/3입니다(rms_x 0.05). 결론을 내리기에는 적습니다.

**한계.** 샘플은 운전자 폴더가 2개라 페이지 설명(43명, 약 20개 차종)만큼 다양하지 않습니다. 차종 정보도 파일에 없습니다. 다양성은 전체 세트가 있어야 확인할 수 있습니다.

## 5. 발견한 문제와 다음 할 일

- **featurize 시작 1분의 rms_z 오류 (SPEC T-22, 해결).** Wf 필터가 0에서 시작해 첫 샘플의 중력 9.81이 계단 입력이 됐습니다. rms_z_1m 중앙값이 첫 1분 1.02, 그 뒤 0.003(시뮬레이터)이었습니다. 필터를 첫 샘플의 정상상태에서 시작하도록 고치고 데이터셋과 모델을 다시 만들었습니다. 첫 1분 중앙값은 0.005가 됐고, 위 표는 고친 뒤 값입니다. 고친 뒤 수직 피처의 KS가 0.95로 커진 것은 시뮬레이터에 수직 저주파 흔들림이 없기 때문입니다 (T-23).
- **시뮬레이터 보정 (SPEC T-23).** 이 비교표를 목표로 `sim_config.json`을 맞춥니다: 고속도로 구간 추가, 가감속·정차 빈도 낮추기, 저주파 횡·수직 흔들림 추가. 국내 도심 분포는 KAIST나 우리 직접 녹화로 맞추는 것이 맞습니다. comma2k19는 미국 고속도로 위주입니다.
- **BATON 전체**: 승인되면 경로별로 받아 피처만 남기고 원본을 지우는 처리로 늘립니다(41 GB, 이 Mac 남은 공간 약 6 GB). 운전자 150명, 차종 99개면 보정 목표의 운전자 차이를 볼 수 있습니다.
- **comma2k19 다른 청크**: `fetch_comma2k19.py --chunk N`으로 늘릴 수 있습니다. 청크마다 약 140 MB입니다.
