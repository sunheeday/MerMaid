## 1. 프로젝트 개요 (MerMaid)

- **목적:** 차량(전기차) 승객의 멀미를 미리 예측하고, 예측 위험도에 따라 차 안의 기기를 켜서 멀미를 줄이는 시스템. 학교 소프트웨어공학 팀 프로젝트.
- **구성:**
  - **차량 컨트롤러:** Raspberry Pi(운영체제 QNX 8.0). IMU(관성 센서)를 I²C로 읽는다.
  - **승객 앱:** Android. 승객이 멀미 설문(MSSQ)을 하고, 주행 중 자기 멀미 정도(MISC)를 입력한다. 폰 GPS 속도를 보낸다.
  - **기기:** 송풍(Tier 1), 차량 화면(Tier 2), 승객 폰 알림(Tier 3).
- **Pi 프로세스 P1~P7:**

  | 프로세스 | 하는 일 |
  |---|---|
  | P1 acq | IMU를 100 Hz로 읽음. 시작할 때 2초 동안 자이로 치우침을 재서 뺌 |
  | P2 feat | 10초마다 피처 71개 계산 |
  | P3 infer | LightGBM 모델로 위험 확률 계산 |
  | P4 policy | 확률과 문턱으로 기기 ON/OFF 결정 |
  | P5 devmgr | 기기 관리 |
  | P6 comm | 폰·기기와 통신 (BLE) |
  | P7 logger | 주행 기록을 SQLite 파일 하나로 저장 |

- **이 작업의 목표:** 실제 차에서 기록한 IMU 데이터를 바로잡아, 모델의 학습 데이터(시뮬레이터)와 **같은 정의**의 데이터로 만드는 것. 그다음 보정 전후의 모델 출력을 비교한다.

## 2. 필요한 사전 지식

### 2-1. 멀미 척도

- **MISC (Misery Scale), 0~10:** 승객이 주관적으로 매기는 멀미 정도.
  - 0: 문제 없음
  - 1: 약간 불편하지만 특정 증상은 없음
  - 2~5: 어지러움, 더위, 두통, 속 불편 등이 "막연히 → 약간 → 중간 → 심하게"
  - 6~9: 메스꺼움이 "약간 → 중간 → 심하게 → 헛구역질"
  - 10: 구토
- **MSSQ (Motion Sickness Susceptibility Questionnaire, 단축형), 0~54점:** 평소 멀미에 얼마나 약한지 묻는 설문. 이 프로젝트의 기본 프로필 값은 12.9이고, 시뮬레이터는 승객의 MSSQ를 평균 12.9, 표준편차 9.9인 정규분포에서 뽑는다.
- **민감도(sensitivity):** MSSQ로 계산하는 계수(`ml/oman.py`의 `oman.sensitivity`). 값의 예: MSSQ 12.9 → 1.000, 26 → 1.487, 33 → 1.839.

### 2-2. Oman 멀미 모델

- 수평 가속도의 크기를 입력으로 받아 멀미 누적 점수를 계산하는 생리학 모델(Oman 1990 계열). 프로젝트 구현은 `ml/oman.py`이다.
- 입력: `c(t) = |LPF(ax), LPF(ay)|`. LPF는 0.63 Hz 2차 저역통과 필터다. **저역통과만 하므로 일정한 값(0 Hz 성분)도 그대로 통과해 점수에 쌓인다.**
- K0 = 51.4. TU Delft 공개 데이터(ATDOMS)에 맞춘 값이다.

### 2-3. IMU 기본

- **가속도계**는 "비력(specific force) = 운동 가속도 − 중력 가속도 벡터"를 잰다. 그래서 평지에 서 있으면 위쪽 축에 +9.81 m/s²가 나온다. 센서나 차가 기울면 중력의 일부가 수평 축에 들어온다. 이렇게 들어온 값은 같은 크기의 실제 가속과 센서 출력만으로는 구분할 수 없다.
  - 기울기 θ일 때 수평 축에 들어오는 값은 g·sinθ다. 1도면 약 0.171 m/s², 1 m/s²이면 약 5.8도다.
- **자이로**는 각속도(rad/s)를 잰다. 치우침(bias)은 P1이 시작할 때 2초 평균으로 뺀다.
- **센서 오차 모델:** 축마다 `측정 = 참값 / 눈금 + 치우침`. 보정은 `참값 = (측정 − 치우침) × 눈금`이다. 축 사이 비직교(cross-axis) 성분은 이 작업에서 다루지 않았다.
- **6면 정지 측정:** 센서의 ±x, ±y, ±z를 각각 위로 향하게 놓고 가만히 둔다. 위를 향한 축은 +g, 아래를 향한 축은 −g가 나와야 한다. 그래서 `치우침 = (위 + 아래)/2`, `눈금 = 2g/(위 − 아래)`로 구한다. 면이 θ만큼 기울면 눈금 오차는 약 1 − cosθ다(2도 → 0.06%).
- **좌표계(이 문서 전체):** 차량 축 기준으로 x 앞, y 왼쪽, z 위. 좌회전이면 원심 가속도가 +y(왼쪽, 회전 중심 방향)로 들어오고 gz도 +다.
- **센서 사양(설정값):** 가속도 범위 ±4 g, 자이로 범위 ±250 도/초, 100 Hz.

### 2-4. 학습 데이터(시뮬레이터)의 정의

이 작업에서 가장 중요한 비교 기준이다. 출처는 `ml/simulator/sim.py` 189~194행, `sim_config.json`, `ml/README.md`이다.

| 축 | 시뮬레이터 IMU에 들어 있는 것 |
|---|---|
| ax (앞뒤) | 운동 가속도 + **g·sin(종단 경사)** + 진동(2~15 Hz) + 잡음 |
| ay (좌우) | 원심 가속도 + 차선 내 흔들림 + 진동 + 잡음. **횡단 경사(도로 좌우 기울기) 없음** |
| az (위아래) | g·cos(종단 경사) + 노면 수직 가속도 + 진동 + 잡음 |
| gy, gz | 경사 변화율, 요 속도 + 잡음 |
| 장착 | 센서가 차와 정확히 같은 축 (기울기·방향 오차 없음), 눈금·치우침 오차 없음 |

- **정답 라벨(MISC)**은 Oman 모델로 만든다. 입력은 **중력과 진동을 뺀 운동 수평 가속도**이고(`sim_config.json` label.input), K = K0 × (실제 민감도) × m이다. 실제 민감도 = MSSQ 민감도 × exp(N(0, 0.65))이다.
- 모델 입력 피처는 위 IMU 값(중력 성분 포함)으로 계산한다. 즉 **라벨은 중력이 없는 값, 피처는 종단 경사 중력이 있는 값**에서 나온다.

### 2-5. 모델

- **LightGBM 이진 분류기 5개.** k = 2~6마다 하나씩, "앞으로 300초 안의 최대 MISC ≥ k일 확률"을 낸다. 출력은 k가 커질수록 작아지게 강제한다(monotone fix).
- **입력 77개.**
  - 차량 피처 71개(10초마다 C++ `featurize`로 계산): rms_x/y/z(10초, 1분, 5분), jerk, yaw_rms, 급가속·급제동·급회전 횟수, pitch_mean_1m, msdv, oman_score, 속도 통계 등. GPS·차량 신호가 없는 칸은 NaN이다.
  - 승객 피처: mssq, sensitivity, ev_experience, vehicle_type 등.
  - 전체 목록은 `protocol/feature_order.json` version 3에 있다.
- **배포 모델 v007, 학습 결과**(맥에서 재현한 v002의 `train/report.md`, 사람 단위 5-fold, 120명, 탑승 1,920회). k=3 PR-AUC 0.860(Oman 점수만 쓰면 0.841), k=4 0.496(Oman만 0.467). **모델 성능이 oman_score 하나만 쓴 경우와 비슷하다.**
- **정책(P4):** Tier 1은 P(≥3) ≥ 0.53이 1주기, Tier 2는 P(≥4) ≥ 0.51이 6주기, Tier 3은 P(≥4) ≥ 0.59가 12주기 이어지면 켠다. 끄는 조건은 확률이 (문턱 − 0.10)보다 낮은 상태가 6주기 이어질 때다. 주기는 10초.
- **개인 보정(B):** `p' = σ(a·logit(p) + b)`. 사람마다 a, b를 주행 기록의 MISC로 맞춘다. 제약은 다음과 같다.
  - a ∈ [0.5, 2.0], |b| ≤ 4
  - 각 Tier 문턱 ±0.05의 p에서 p − p' ≤ 0.10. 넘으면 b를 올린다.
  - 라벨 있는 주행이 2개 이상이고, 한 주행씩 빼고 맞춘(leave-one-ride-out) log loss가 좋아져야 채택한다.
  - 자동 적용이 아니다. 맥이나 서버에서 계산한 뒤 Pi의 `state/calib/`에 넣어야 한다.

## 4. 보정 목표의 정의

"학습 데이터와 같은 정의"를 다음과 같이 정했다.
1. 축이 차량 축(x 앞, y 왼쪽, z 위)과 같다.
2. 차가 평지에 서 있을 때 (0, 0, +g)가 나온다.
3. 각 축이 1 g를 9.80665로 읽는다.
4. 샘플이 정확히 10 ms 간격이다.
5. 앞뒤에 종단 경사 중력은 남긴다(시뮬레이터에 있으므로). 좌우 횡단 경사는 시뮬레이터에 없다. 그래서 빼는 것(5단계 ②)을 시험했고, 기본으로 넣을지는 정하지 않았다.

## 5. 보정 단계 요약

적용 순서는 3 → 1 → 2 → 6(표시) → 4(시간축 재표본화)이고, 5는 별도 시험이다. 단, 6단계 판정은 3·1·2를 적용하기 전의 원본 값으로 한다(6-4). 단계 번호는 계획 문서의 번호이며 적용 순서와 다르다.

| 단계 | 바로잡는 오차 | 상태 |
|---|---|---|
| 3 센서 오차 | 축별 치우침·눈금 | y·z 적용(6면 측정), x는 치우침 0·눈금 1 |
| 1 장착 기울기 | 센서가 차에 기울어 붙은 것 | 적용 |
| 2 방향(요) | 센서 x축이 차 진행 방향과 수평으로 어긋난 것 | 추정만, 적용 안 함 |
| 6 이상값 | 빠진 샘플, 포화 | 표시만 함 (값은 그대로) |
| 4 시간축 | 샘플 간격이 정확히 10 ms가 아님 | 적용 |
| 5 경사 중력 | 도로 경사로 들어온 중력 | 기본에는 넣지 않음. 2일차에 좌우만 따로 시험 |

## 6. 단계별 방법 (코드: `imu_calib/imu_calib.py`, 적용: `run_calibration.py`)

### 6-0. 정지 구간 찾기 (`find_still_windows`)
- 1초씩 자른다. 1초 평균 각속도의 크기가 0.6 도/초 미만이고, 수평 가속도 표준편차(x, y 중 큰 쪽)가 0.06 m/s² 미만이면 "조용한 1초"로 본다.
- 조용한 1초가 3초 이상 이어지면 정지 구간이다. 검증과 기울기 기준에 쓴다.

### 6-1. 3단계: 센서 오차
- **식:** `acc_s = acc_car · R` (차 축 → 센서 축), `acc1 = ((acc_s − bias) ⊙ scale) · Rᵀ`. R은 `R_car_from_sensor`다. 치우침·눈금은 센서 칩 축의 값이므로 센서 축에서 적용한다.
- **6면 측정 결과** (`sensor_6face.json`)

  | 축 | 위 면 | 아래 면 | 치우침 | 눈금 |
  |---|---|---|---|---|
  | x | 없음 | −9.710 | 0 (정할 수 없음) | 1 (정할 수 없음) |
  | y | +9.839 (7 s, 1.7도 기움) | −9.787 (8 s, 1.2도) | +0.0263 | 0.99937 |
  | z | +9.912 (50 s, 0.7도) | −9.913 (19 s, 1.4도) | −0.0003 | 0.98931 |

  - 면이 기운 각도는 평균 벡터와 해당 축 사이의 각도다.
  - 정지 판별 조건은 이 측정에서만 완화했다(자이로 1.5 도/초, sd 0.15). 표준 스크립트(`six_face.py`, 15초 이상, 0.6 도/초, sd 0.05)로는 +x, −x, +y, −y를 찾지 못했다. ±y 면은 7~8초로 짧다.
  - +x 면은 기록에 없다. −x 하나만으로는 x 치우침과 x 눈금을 분리할 수 없다. 모든 정지 자세의 크기가 g가 되도록 6개 매개변수를 최소제곱으로 맞춰 봤지만 조건수가 598이었다. 그래서 x는 치우침 0, 눈금 1로 두었다.
- **x를 비워 둔 영향(추정):** x 치우침은 1단계 회전이 정지 기준 구간의 수평 값을 0으로 만들면서 함께 상쇄된다. 다만 상쇄는 기준 자세에서만 정확하다. x 눈금 오차는 이 칩의 다른 축이 0.06%(y), 1.07%(z)였으므로 1% 안팎으로 추정하며, 측정하지 않았다.
- **이전 방법(1점 z 눈금):** 6면 측정 전에는 기울기 기준 구간의 평균 (x, y, z)로 `s = √(g² − x² − y²)/z`를 구해 z 눈금만 바로잡았다. 1일차 0.98948, 2일차 0.98970이었다. 6면 측정의 z 눈금 0.98931과 차이는 0.02~0.04%다.
- **온도:** 1일차 정지 구간의 가속도 크기가 출발 후 약 35분 동안 9.912에서 9.893으로 줄었다. 온도 보정은 하지 않았다.

### 6-2. 1단계: 장착 기울기
- 출발 전 정지 구간(사람이 모두 탄 뒤, 사용자가 시각 지정)의 평균 가속도 m을 구한다. m을 z축으로 보내는 최단 회전을 로드리게스 식으로 만든다: `v = m̂ × ẑ`, `R = I + [v]× + [v]×²/(1 + m̂·ẑ)`. 회전축이 수평면 안에 있어 요 방향은 바꾸지 않는다.
- 가속도와 자이로 모두에 같은 R을 적용한다.
- **결과**

  | | 기준 구간 | 정지 평균 (3단계 적용 후) | 앞뒤 | 좌우 |
  |---|---|---|---|---|
  | 1일차 | 316~324 s | (+0.498, −0.383, +9.784) | +2.92도 | −2.24도 |
  | 2일차 | 54~108 s | (+0.102, −0.121, +9.802) | +0.60도 | −0.71도 |

- **가정:** 기준 정지 구간의 바닥이 수평이다. 확인하지 않았다. 바닥이 기울어 있으면 그 기울기가 장착 기울기로 잘못 들어간다.

### 6-3. 2단계: 방향(요)
- **방법 1** (`estimate_yaw_offset`): 기울기를 보정한 뒤 1초 평균을 쓴다. |gz| < 1.5 도/초이고 |수평 가속| > 0.3인 초만 골라, 원점을 지나는 주성분 방향의 각도를 구한다. 불확실도는 부트스트랩 300회로 구한다.
  - 1일차 +0.06 ± 1.02도(48초), 2일차 −1.94 ± 1.29도(929초)
- **방법 2** (2일차만, GPS 사용): 30초 고역통과(30초 이동평균을 뺌)한 뒤 두 가지를 구한다.
  - (ay − v·gz)를 dv/dt에 회귀해 +ψ
  - (ax − dv/dt)를 v·gz에 회귀해 −ψ
  - 두 값의 평균은 +0.19 ± 1.59도(30초 블록 부트스트랩)
- 두 방법 모두 0과 구분되지 않아 **적용하지 않았다.** 1.5도가 어긋나 있다면 다른 축 값이 약 2.6% 섞인다.

### 6-4. 6단계: 이상값 표시
- 결과 파일의 8번째 열 flag에 표시한다. 비트 1 = hold(빠져서 직전 값으로 채운 샘플), 비트 2 = 포화(어느 축이든 범위의 98% 초과).
- 값은 지우거나 보간하지 않는다.
- 판정은 3·1·2단계를 적용하기 전의 원본 값(차 축으로 축 순서만 바꾼 값)으로 한다(`run_calibration.py`의 `flag_samples(acc, gyro, …)`, `acc`는 원본).
- 4단계 재표본화 뒤의 flag는 각 새 시각의 바로 뒤 원래 샘플의 flag를 따른다. 보간에 쓰인 앞뒤 두 샘플의 flag를 합치지(OR) 않으므로, 앞 샘플에만 붙은 표시는 빠질 수 있다. 모델 피처는 flag를 쓰지 않는다.

### 6-5. 4단계: 시간축
- 원본 기록에는 1초 묶음마다 Pi 단조 시계(mono_ns0)가 찍혀 있다. 묶음 번호(seq0) → 시각에 3차 다항식을 맞춰 각 샘플의 실제 시각을 구한다. 그 시각에서 정확히 0.01 s 간격으로 선형 보간해 다시 뽑는다.
- **결과**

### 6-6. 5단계: 경사 중력 (`cross_slope.py`, 2일차만, 시험)
- **선택지**
  - ① 그대로 둠 (현재 기본)
  - ② 좌우 ay에서만 뺌
  - ③ ax, ay 모두에서 뺌
  - ③은 시뮬레이터 ax에 종단 경사 중력이 있으므로 모델 입력과 정의가 달라진다. 그래서 시험하지 않았다.
- **② 방법:**
  - GPS 속도를 IMU 쪽으로 0.8 s 당긴다. 이 지연은 `gps_check.py`가 ax와 dv/dt의 상관이 가장 큰 지연을 −3~+3 s에서 찾은 값이다.
  - 1초 격자에서 `resid = ay − v·gz`를 구한다. 느린 성분을 고르는 방법이 두 가지다(`--method`).
    - **mean (처음 방식):** GPS가 있는 모든 초의 30초 이동평균. → `calibrated_xslope/`
    - **median (11-24 추가, 기본):** GPS 정확도(폰이 보낸 acc 열) ≤ 10 m이고 |gz| < 1도/초인 초만 골라 120초 창 중앙값을 낸다(창 안에 고른 초가 20개 미만이면 앞뒤 값으로 잇는다). GPS 구간 경계에서는 0과 값 사이를 5초에 걸쳐 잇는다. 2일차 GPS 1427초 중 978초를 썼다. → `calibrated_xslope2/`
  - 이를 100 Hz로 보간해 ay에서 뺀다. GPS가 없는 구간(174.5 s 이전, 1600.5 s 이후)은 빼지 않는다.
- **뺀 값 (mean):** 주행 중 중앙값 +0.316 m/s²(약 1.8도), 10~90% 범위 −0.007 ~ +0.447, 정차 중 중앙값 +0.324. GPS가 막 잡힌 175~200 s에는 −0.47을 뺐다(이 구간은 차가 1 m/s 안팎으로 움직였고 GPS 정확도가 6~25 m였다). 경계에서 1초 사이 최대 0.37 변했다.
- **뺀 값 (median):** 주행 중 중앙값 +0.310, 10~90% 범위 +0.088 ~ +0.435, 정차 중 중앙값 +0.327. 175~240 s는 +0.13~+0.38. 1초 사이 최대 변화 0.08.
- **한계**
  - 뺀 값에는 도로 횡단 경사, 1단계 기준 자리의 좌우 기울기, 장착 잔여 오차, 차체 롤이 섞여 있고 서로 구분하지 못한다.
  - GPS가 처음 잡힌 175~230 s는 resid가 ±1.4까지 흔들린다. median 방식은 이 구간의 초 대부분을 정확도·직진 조건으로 뺀다.
  - 120초 창, |gz| < 1도/초, 정확도 10 m는 정한 값이며 다른 값과 비교하지 않았다.
  - 주행 하나에만 시험했다.
- **종단 경사(ax) 확인 시도:** `ax − dv/dt`의 10초 평균은 중앙값 +0.063, 10~90% 범위 −0.290 ~ +0.421 m/s²(−1.7 ~ +2.5도)이다. 폰 GPS 고도로 구한 경사와의 상관은 0.07로, 종단 경사인지는 확인되지 않았다.

**V2·V9 해석에 대한 주의:** 기준이 아닌 정지 구간의 수평 값은 그 자리의 바닥 경사와 보정 잔차가 합쳐진 값이다. 둘은 분리되지 않는다.

**V3 2일차가 약한 이유는 확인하지 않았다.** 2일차 진동 sd는 1일차의 약 2배다(앞뒤 0.22, 좌우 0.18, 위아래 0.34).

**단계 적용 확인** (`check_applied.py`): 보정 코드를 다시 부르지 않고, 원본과 `calibration.json` 값만으로 결과를 다시 만들어 보정 결과 파일과 샘플마다 비교했다. 단, 시간축 다항식은 같은 함수를 쓴다. 차이는 가속도 0.00000 m/s², 자이로 0.00001 도/초 이하로 1·2일차 모두 같다. 이 검사는 "기록된 값이 기록된 대로 적용됐는가"만 확인한다. 값 자체가 맞는지는 확인하지 않는다.

## 10. 가정, 한계, 미결정 사항

1. 1단계 기준 정지 구간의 바닥이 수평이라는 가정을 확인하지 않았다.
2. x축 치우침·눈금을 측정하지 못했다(+x 면 없음). 축간 비직교는 모델에 없다.
3. 1일차 정지 가속도 크기가 약 0.02 m/s² 변했다(원인 미확인, 온도는 기록하지 않음). 보정하지 않았다. 6면 측정 때 Pi가 켜진 지 얼마나 됐는지는 기록하지 않았다(직전에 다른 기록이 돌고 있었음).
4. 2단계(요)는 두 방법 모두 ±1.3~1.6도 불확실도 안에서 0과 구분되지 않는다.
5. 5단계: 좌우 제거(②)는 주행 하나에만 시험했다. median 방식의 매개변수(120초, 1도/초, 10 m)는 비교 없이 정했다. 제거된 값의 구성(도로, 기준 자리, 롤)을 분리하지 못한다. 종단 경사는 확인할 기준 데이터(지도 고도, 기압계)가 없다.
6. V7 상관이 0.84~0.86으로 기준 0.95 미만이다. V8(정차 간 적분)은 실패했다.
7. V4는 하지 않았다. V11은 11-24에 했다(7절).
8. 2일차 1600 s 이후를 제외한 판단은 사용자에게 확인받지 않았다.
9. 2일차 피처 재현 차이(B vs A 확률 2.7e-2)의 원인을 찾지 않았다.
10. 승객이 1명, 주행이 2회, MISC ≥ 4 라벨이 1개다. 모델 출력과 MISC를 비교한 결론은 통계적으로 약하다.
11. Pi는 주행 중에 이 보정(1·3·4·5단계)을 적용하지 않는다. 8절의 D·E는 오프라인 결과이고, Pi가 다음 주행에서 낼 확률은 C에 가깝다(장착 축이 맞는 경우).
12. 개인 보정 값을 Pi에 넣는 경로: `run_live.sh`가 주행마다 새 state 폴더를 만들기 때문에, 미리 넣어 둔 보정 파일을 다음 주행이 읽지 못한다. 저장소 수정이 필요하며, 하지 않았다.
13. 시뮬레이터의 MSSQ → 민감도 관계, 그리고 라벨(중력 없음)과 피처(중력 포함)의 정의 차이는 모델 쪽 사안이며 다루지 않았다.
14. 자이로 눈금을 보정하지 않았다. 6면 측정 회전으로 거칠게 구한 값은 1.01~1.04다(7절 V6).
15. 4단계 재표본화 뒤 flag는 한쪽 이웃만 따른다(6-4).
