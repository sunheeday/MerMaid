1문서 개요

1.1목적

MerMaid 시스템 중 탑승객이 직접 보는 화면(탑승객 앱, 차량 디스플레이, HUD)이 갖춰야 할 기능·품질·인터페이스 요구사항을 정의한다. 개발·테스트·발표 검수의 기준으로 쓴다.

1.2변경 배경 (v0.1 웹 시제품 → v0.2 Android 앱)

탑승객은 MerMaid 앱을 “보는” 것이 아니라, 켜 두고 다른 앱을 쓴다

  • v0.1 시제품(cabin3d/ui/app.html)은 앱 안의 영상 위에만 모션 큐를 그렸다.
  • 실제 탑승 중 사용은 대부분 YouTube·SNS 등 타 앱이다. 큐가 그 앱 위에 나타나야 의미가 있다.
  • 따라서 앱은 차에 타면 자동으로 차량(컨트롤러)과 연결되어 백그라운드에 상주하고, Tier 3 명령이 오면 시스템 오버레이로 타 앱 위에 모션 큐를 그린다.
  • 웹 페이지로는 타 앱 위에 그릴 수 없으므로 Android 네이티브 앱(Kotlin)으로 다시 개발한다. 대상 기기는 Galaxy S22+.

1.3범위

구성요소이번 버전 범위비고
탑승객 앱 (Android)자동 연결·백그라운드 상주, 타 앱 위 모션 큐 오버레이, 상주 알림·빠른 설정 타일, 수동 조작, 멀미 프로필(MSSQ-Short), 설정·RF 진단신규 개발 (PRD 단계 S9)
차량 디스플레이 (웹, role hud)개입 상태, 송풍·앰비언트 수동 조작, 화면 모션 큐, 가속도 표시v0.1 유지, 일부 보완
HUD (웹, role hud)가속 방향 앰비언트 큐, 반사 모드, 디스플레이 연결 공유v0.1 유지 (PRD 단계 S8)
제외컨트롤러(P1~P6)·브리지 펌웨어 변경, 운전 기능 제어, iOS 앱, 음성 입력프로토콜 변경 없음

차량 디스플레이 · HUD (웹)

role hud, 기기 ID 항상 hud-01. 같은 브리지에 BLE(Web Bluetooth)로 붙거나, 시연 때는 로컬 백엔드(backend/server.py)의 WebSocket으로 붙는다. HUD 창은 디스플레이의 연결을 공유한다 (hud-01은 한 연결만 등록).

판단은 컨트롤러, 앱은 표시·전달

언제 무엇을 켤지는 P4가 정한다. 앱은 INT·MOT를 받아 그리고, 화면 상태(SCR)·수동 조작(OVR)·프로필(PROF)을 보낸다. 앱 안에서 위험도를 계산하지 않는다.

2.3탑승객 앱 연결 상태

미등록→ 차량 등록 → 대기→ 브리지 감지 → 연결 중→ HELLO 송신 → 연결됨→ 5초 무수신 → 신호 없음 (안전 OFF)→ 수신 재개 → 연결됨 / 끊김 → 재연결

“대기”는 FGS 없이 시스템(CDM)이 감시하는 상태다. 브리지가 범위에서 사라지면 다시 “대기”로 돌아가고 상주 알림을 내린다.

7제약 · 가정

  • 프로토콜 v1(protocol/)은 바꾸지 않는다. 앱은 그 계약 안에서만 동작한다.
  • 판단(언제 켤지)은 컨트롤러 P4가 한다. 앱은 위험도를 계산하지 않는다.
  • 오버레이 앱은 Google Play 정책 심사 대상이다. 이번 버전은 데모용 사이드로드(APK) 배포를 가정한다.
  • 가속 축 규약 ax+ = 앞, ay+ = 왼쪽(ISO 8855)은 임시(RF_MESSAGES §5). 확정되면 점 이동 방향 부호만 바꾼다.
  • 현재 개발 PC에는 Android SDK·JDK가 없다. 빌드·실기 시험은 Android Studio 설치 후 진행한다.
